## Execution rules and dependencies

Perform phases in order; within a phase follow listed dependencies. Keep changes small and record milestone commits rather than manufacturing commit history at the end. Put behavior tests next to the boundary/component they verify; do not test framework internals or chase a coverage percentage. Use fixture-backed checks for the default suite. API discovery is the first risk gate; unsupported contracts remain explicit blockers or limitations rather than guessed implementation facts. Update the affected specs/design/traceability before coding any material deviation.

## Reversal and failure handling

At each gate, preserve the last verified commit. If a change fails, fix it or revert the specific milestone commit without discarding unrelated user work. A cache-format change uses a versioned key and safely discards only incompatible application-owned product entries; cart count and unrelated storage survive. An eventual optional hosted release can restore the previous verified build, but static SPA fallback must still be checked. Neither reverting code nor timing out a request reverses a remote cart mutation. Record uncertain outcomes and never compensate by guessing another API call.
